# 🎯 Enterprise Technical Interview Q&A Guide

Comprehensive questions and detailed answers based on the **Mini Enterprise AI Knowledge Assistant** project. Use this guide to prepare for Senior Python, AI/ML Engineer, DevOps, and Full-Stack interviews.

## 🧠 Part 1: Generative AI, RAG & Vector Databases

### Q1: What is Retrieval-Augmented Generation (RAG) and why is it preferred over Fine-Tuning?
**Answer:**  
RAG is an architectural pattern that combines an information retrieval system with a generative language model:
1. **Retrieval:** When a user queries the system, relevant chunks of data are retrieved from an external knowledge base (e.g. ChromaDB).
2. **Augmentation:** These chunks are injected into the prompt as factual context.
3. **Generation:** The LLM generates a grounded answer strictly based on that context.

**Why RAG is preferred over Fine-Tuning:**
* **Hallucination Prevention:** Fine-tuned models still hallucinate; RAG grounds answers directly in source text with page citations.
* **Instant Knowledge Updates:** When enterprise documents change, updating a vector database takes seconds. Fine-tuning requires hours/days of retraining.
* **Cost & Computation:** RAG runs on affordable compute using lightweight embedding models (like `all-MiniLM-L6-v2`), while fine-tuning large models requires expensive GPU clusters.
* **Access Control & Auditing:** RAG allows document-level access filtering and transparent citations.

### Q2: What is the purpose of Text Chunking, and how did you select your chunk size?
**Answer:**  
LLMs have finite context windows, and embedding models perform poorly when processing long text because sentence-level semantic meaning gets diluted over long passages.  
* In our project, we used **LangChain's `RecursiveCharacterTextSplitter`** with a `chunk_size` of **700 characters** and a `chunk_overlap` of **150 characters**.
* **Why 700 characters?** It is roughly 100-150 words, representing a coherent paragraph containing a single complete thought.
* **Why 150 overlap?** The overlap ensures that sentences or definitions occurring at chunk boundaries are not abruptly truncated, preserving semantic continuity across consecutive chunks.

### Q3: What are Dense Vector Embeddings and how does ChromaDB perform similarity search?
**Answer:**  
Vector embeddings are high-dimensional numerical vectors (in our project, 384 dimensions generated by `all-MiniLM-L6-v2`) where semantically similar texts are placed close to each other in vector space.  
* ChromaDB stores these vectors and uses **Cosine Similarity** (or Cosine Distance: $1 - \cos(\theta)$) to measure the angle between the query vector and document vectors.
* For large-scale search, ChromaDB implements **Approximate Nearest Neighbor (ANN)** indexing using HNSW (Hierarchical Navigable Small World graphs), enabling sub-millisecond retrieval across thousands of document chunks.

### Q4: How do you prevent hallucinations in your LLM generation?
**Answer:**  
We employ prompt-level system guardrails:
1. The prompt explicitly instructs: *"Answer the user's question accurately and concisely using ONLY the provided document context below."*
2. We include a negative constraint: *"If the answer cannot be found in the context, clearly state: 'The requested information is not available in the provided document.' Do not attempt to extrapolate or guess."*
3. We require mandatory source attribution: *"Always cite the specific page number(s) where the answer was found."*

## 🚀 Part 2: Backend & System Architecture (FastAPI & Streamlit)

### Q5: Why did you choose FastAPI over Flask or Django for the backend?
**Answer:**  
1. **Asynchronous Performance:** FastAPI is built on Starlette and ASGI, supporting high concurrency for I/O-bound tasks (file parsing, network queries to LLMs).
2. **Automatic Data Validation:** Uses Pydantic to strictly validate request and response payloads with detailed error messages.
3. **Automated Documentation:** Generates interactive OpenAPI (Swagger) documentation automatically at `/docs`.
4. **Lightweight:** Unlike Django, FastAPI does not impose heavy ORM or session overhead that is unnecessary for a dedicated AI microservice.

---

### Q6: How does PyMuPDF extract text, and how does it compare to other PDF libraries like PyPDF2?
**Answer:**  
PyMuPDF (built on the C-based MuPDF engine) is significantly faster (typically 10x-20x faster than pure-Python libraries like PyPDF2) and provides accurate layout parsing, font handling, and exact page-by-page metadata extraction. It also allows detecting whether a page has raw text or is an empty scanned raster image.

## 🐳 Part 3: Containerization & DevOps (Docker)

### Q7: Explain the multi-container architecture in your `docker-compose.yml`.
**Answer:**  
Our system uses a decoupled microservices design:
* **Service 1 (`backend`):** Runs FastAPI, PyMuPDF, and ChromaDB on port 8000.
* **Service 2 (`frontend`):** Runs the Streamlit user interface on port 8501, communicating with the backend over an isolated bridge network (`http://backend:8000`).
* **Volume Persistence:** Named volumes (`pdf_data` and `chroma_data`) are mounted to `/app/data/uploads` and `/app/chroma_db`. This ensures that even if containers are destroyed or updated, user documents and vector embeddings remain intact.
* **Health Dependency:** The frontend container waits for the backend container's HTTP healthcheck to succeed before starting (`condition: service_healthy`).

---

### Q8: What is `.dockerignore` and why is it critical?
**Answer:**  
When building a Docker image, Docker sends the entire directory context to the Docker daemon. `.dockerignore` excludes unnecessary files:
* `.venv` (local Windows virtual environment binaries that are incompatible with Linux containers).
* `__pycache__` and `.git` (which inflate image size unnecessarily).
* `.env` files (preventing accidental leakage of secret keys into image layers).

## ☸️ Part 4: Kubernetes & Orchestration (Minikube)

### Q9: What is the difference between a Pod, a Deployment, and a Service in Kubernetes?
**Answer:**  
* **Pod:** The smallest deployable unit in Kubernetes, consisting of one or more co-located containers sharing network namespace and storage.
* **Deployment:** A controller that declares the desired state for Pods (e.g. 2 replicas, rolling updates, self-healing pod replacements).
* **Service:** An abstraction that defines a logical set of Pods and a policy to access them. Since Pod IPs are ephemeral and change upon restart, a Service provides a stable IP address and DNS name with internal load balancing.

---

### Q10: Why did you use `ClusterIP` for the backend and `NodePort` for the frontend?
**Answer:**  
* **`backend-service` (ClusterIP):** Only accessible internally within the Kubernetes cluster. The frontend communicates with it via internal DNS (`http://backend-service:8000`). This secures the backend API from direct unauthorized public internet access.
* **`frontend-service` (NodePort):** Exposes port `30501` on every cluster node, allowing users to access the Streamlit UI directly from their web browser.

---

### Q11: Explain how you implemented High Availability (HA) and Self-Healing in Kubernetes.
**Answer:**  
1. **Replicas:** Both backend and frontend deployments define `replicas: 2`. If one pod crashes, the second continues serving traffic without downtime.
2. **Liveness Probes:** Periodically checks `/health` and `/_stcore/health`. If a container hangs or deadlocks, kubelet automatically restarts the container.
3. **Readiness Probes:** Ensures pods only receive user traffic after their dependencies (ChromaDB, models) have finished booting.
4. **PersistentVolumeClaims (PVC):** Ensures stateful data is mounted from cluster storage rather than ephemeral container disks.

## 📊 Part 5: Observability & CI/CD (Prometheus, Grafana, Loki & GitHub Actions)

### Q12: What metrics do you track in Prometheus, and why?
**Answer:**  
We track four Golden Signals of observability:
1. **Request Rate (RPS):** `rate(http_requests_total[1m])` to monitor incoming traffic volume.
2. **Latency (p95 / p99):** `histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[1m]))` to measure response times and detect performance degradation.
3. **Errors:** HTTP 4xx and 5xx counts by endpoint to spot API failures.
4. **Business & AI Metrics:** `chromadb_chunks_total` (size of vector index) and `rag_queries_total` (usage of AI search).

---

### Q13: Why did you choose Loki over traditional Elasticsearch/ELK for logging?
**Answer:**  
* **Index-Free Log Storage:** Unlike Elasticsearch which indexes every word of every log line (consuming enormous RAM and disk), Loki only indexes metadata labels (e.g. `service="backend-api"`).
* **Cost & Efficiency:** Loki uses orders of magnitude less memory and storage than ELK.
* **Native Grafana Integration:** Allows correlating metrics and logs side-by-side in a single Grafana dashboard.

---

### Q14: Describe your GitHub Actions CI/CD Pipeline.
**Answer:**  
Our automated pipeline (`.github/workflows/ci-cd.yml`) triggers on every push and pull request with 3 sequential gates:
1. **Testing Gate (CI):** Installs Python 3.11 with pip caching and runs all 34 automated unit, RAG, and integration tests.
2. **Container Build Gate:** Builds and validates Docker images for backend and frontend using Buildx.
3. **Kubernetes Validation Gate (CD Prep):** Performs dry-run schema validation (`kubectl apply --dry-run=client -k k8s/`) across all Kubernetes manifests to catch configuration errors before reaching production.
